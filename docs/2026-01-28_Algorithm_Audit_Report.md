## 二、关键缺陷清单

### ~~缺陷1: CAS模块权重逻辑错误~~ [已验证正确]

**文件**: `src/cas_selector.py`

**原问题**: 误认为 `w_direct_dist_bs = -0.5` 逻辑错误。

**实际分析**:
- `dist_bs` 是归一化距离，**值越高 = 距离BS越远**
- `w_direct_dist_bs = -0.5`：距离越远，Direct模式得分越**低** (正确！)
- `w_chain_dist_bs = 0.2`：距离越远，Chain模式得分越**高** (正确！)
- `w_twohop_dist_bs = 0.5`：距离越远，TwoHop模式得分越**高** (正确！)

**结论**: CAS权重逻辑设计正确，符合物理直觉。

---

### ~~缺陷2: Gateway中心性定义错误~~ [已验证合理]

**文件**: `src/gateway_selector.py`

**原问题**: 误认为中心性定义非标准。

**实际分析**:
```python
# centrality proxy: inverse of mean distance to other CHs
centralities[ch.id] = 1.0 / (mean_d + 1e-9)
```

这是**接近中心性(Closeness Centrality)的简化版本**：
- 标准定义: `C(v) = (n-1) / Σd(v,u)`
- 当前实现: `C(v) = 1 / mean(d(v,u))`
- 两者在排序上等价，计算更高效

**结论**: Gateway中心性定义合理，无需修改。

---

### 缺陷3: Skeleton PCA假设不成立 [中等]

**文件**: `src/skeleton_module.py`

**问题**: PCA主成分方向假设节点呈线性分布，对uniform/clustered拓扑无效。

**影响**: 在非线性拓扑下，Skeleton骨干网络可能偏离最优路径。

---

### ~~缺陷4: 能量模型单位混淆~~ [已验证正确]

**文件**: `src/improved_energy_model.py`

**原问题**: 误认为单位不一致。

**实际验证**:
- `tx_energy_per_bit`: 208.8e-9 J/bit = 208.8 nJ/bit
- 放大器能耗使用 `1e-9` 和 `1e-12` 系数进行单位转换
- 计算结果: 1KB数据 @ 50m = 1751 uJ
- 文献典型值: CC2420 @ 250kbps = 1710 uJ
- 误差: ~2.4% (合理)

**结论**: 能量模型单位一致，计算正确。

---

### ~~缺陷5: PDR计算不连续~~ [已验证连续]

**文件**: `src/realistic_channel_model.py`

**原问题**: 误认为PDR函数在边界点不连续。

**实际验证**:
- rssi=-70: 0.99 (上界) vs 0.5+0.49*10/10=0.99 (下界) -> 连续
- rssi=-80: 0.5 (上界) vs (85-80)/5*0.5=0.5 (下界) -> 连续

**结论**: PDR函数在边界点连续，设计正确。

---

### 缺陷6: 动态场景实为静态快照 [设计限制]

**问题**: "动态走廊"、"移动基站"实际是多个独立静态快照，非真正动态仿真。

**分析**: 这是常见的仿真设计方法，通过多个静态快照近似动态变化。
- 优点: 实现简单，结果可重复
- 缺点: 无法捕捉协议对瞬时变化的响应

**建议**: 在论文中明确说明这是"准静态"(quasi-static)仿真方法。

---

### ~~缺陷7: 数据伪造嫌疑~~ [已验证安全]

**文件**: `src/aeris_protocol.py`

**原问题**: 误认为 `force_ctp_reliable=True` 会导致数据伪造。

**实际验证**:
- `force_ctp_reliable` 默认值为 `False`
- 所有实验脚本显式设置 `force_ctp_reliable = False`
- 该参数仅用于特殊测试场景，不影响正常实验

**结论**: 无数据伪造风险，设计合理。

## 四、5轮深度自查结果 (2026-01-28 补充)

### 自查第1轮: CAS权重不平衡 [已修复]

**发现问题**: 虽然CAS权重逻辑正确，但三种模式的权重和严重不平衡：
- Direct模式权重和: 0.2 (过低)
- Chain模式权重和: 1.8
- TwoHop模式权重和: 1.7

**影响**: 近距离节点几乎永远不会选择Direct模式，即使Direct是最优选择。

**修复方案**: 重新平衡权重 (`src/cas_selector.py`)
```python
# 修复后的权重配置
w_direct: 0.4+0.5-0.3-0.2+0.3-0.1 = 0.6 (基础) + 距离优势
w_chain:  0.3+0.3+0.2+0.3+0.2-0.1 = 1.2
w_twohop: 0.3+0.3+0.4+0.2+0.1-0.1 = 1.2
```

**验证结果**:
```
近距离节点 (dist_bs=0.1): Direct=0.800 > Chain=0.690 > TwoHop=0.630
远距离节点 (dist_bs=0.9): TwoHop=0.920 > Chain=0.850 > Direct=0.440
```

## 五、深度自查发现的严重缺陷 (2026-01-28 补充)

### 缺陷8: 基线协议PDR=1.0 [严重]

**发现时间**: 分析8小时实验结果时发现

**问题描述**:
基线协议(LEACH/PEGASIS/HEED/TEEN)的PDR全部为1.000，无任何丢包。

**根本原因**:
```python
# benchmark_protocols.py 第62行
enable = bool(getattr(config, "enable_channel", False))  # 默认False

# 第72-74行
def _link_success(channel_model, ...):
    if channel_model is None:
        return True  # channel_model为None时永远返回True!
```

实验脚本未设置 `enable_channel=True`，导致基线协议不模拟链路丢包。

**影响**:
- 基线协议PDR=1.0，AERIS PDR=0.91，对比不公平
- 实验结论可能被质疑

**修复方案**:
在实验脚本的NetworkConfig中添加 `enable_channel=True`

**修复验证**:
```
修复前: LEACH PDR = 1.000
修复后: LEACH PDR = 0.707, PDR_e2e = 0.270
```

**状态**: ✅ 已修复 (`scripts/run_mega_8h.py`)

---

### 缺陷9: PDR指标定义不一致 [重要发现]

**发现时间**: 修复后对比测试时发现

**问题描述**:
实验使用 `packet_delivery_ratio` (链路级PDR)，但真正有意义的是 `packet_delivery_ratio_end2end` (端到端PDR)。

**对比结果** (100节点, 200轮):
| 协议 | 链路级PDR | 端到端PDR |
|------|-----------|-----------|
| AERIS | 0.839 | **0.995** |
| PEGASIS | 0.917 | 0.460 |

**分析**:
- PEGASIS链路级PDR高(0.917)，但端到端仅0.460
- AERIS端到端PDR(0.995)是PEGASIS的2倍以上
- **AERIS的真正优势在于端到端可靠性**

**建议**:
论文应强调端到端PDR指标，这是AERIS的核心优势。
